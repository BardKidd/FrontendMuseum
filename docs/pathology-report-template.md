# 病理報告文字模板

> 每個標本一份。**這份模板的目的不是好看，是讓讀者能判斷該不該相信這些數字。**
>
> 用法：整段複製，把 `⟨⟩` 換掉。**不准刪節** —— 刪掉的通常正是讀者用來質疑你的那一節。
> 沒有數字的欄位寫「未量測」，不要留空，也不要填 0。「未量測」與「量到 0」是兩件事，
> 標本 #3 治療版的全部結論就建立在這個區別上。

## 版型

### ⟨編號⟩ ⟨標本名稱⟩

**病症一句話**：⟨在什麼操作下、哪個指標、壞到什麼程度⟩

#### 凍結條件

同一組條件之間才能比較。任何一項改動，先前所有數字作廢。

| | |
|---|---|
| CPU throttle | ⟨1x / 4x / 6x⟩ —— **宣告值**，JS 偵測不到 |
| 驅動方式 | ⟨人手 / CDP 機器驅動⟩ |
| viewport | ⟨w × h⟩（CLS 與 LCP 都是 viewport 相對量） |
| refreshHz | ⟨實測值⟩（掉幀門檻由它推導，不是寫死 16.7ms） |
| 操作程序 | 動作 ⟨click/scroll/type/stream⟩ · 次數 ⟨n⟩ · 間隔 ⟨ms 或「盡快連續」⟩ |
| buildId | ⟨id⟩ |
| protocolVersion | ⟨n⟩ |

#### 動工前登記的預期

> 登記出處：`⟨docs/phaseN-expected-results.md:行號⟩`
> **這一節不准回頭改去迎合實測。** 要修正就在該檔案的「修正紀錄」追加。

- 主指標：⟨metric⟩，預期 ⟨區間⟩
- 兇手段：⟨inputDelay / processing / presentation / loaf / lcp / cls⟩
- 病變 vs 治療比值：⟨預期⟩
- 登記在案的風險：⟨動工前就寫下的、可能讓這個標本失敗的原因⟩

#### 實測

三輪，同一組凍結條件。**離散度算在每輪的 median 上，不是 max** ——
`protocol.ts:290`：「抗離群。可重現性判定用這個，不用 max」。

| mode | 三輪主指標 | 相對離散度 | 絕對全距 | 判定 |
|---|---|---|---|---|
| ⟨病變⟩ | ⟨v1 / v2 / v3⟩ | ⟨%⟩ | ⟨range⟩ | ⟨可重現 / 不可重現⟩ |
| ⟨治療⟩ | ⟨v1 / v2 / v3⟩ | ⟨%⟩ | ⟨range⟩ | ⟨…⟩ |

判準：相對離散度 ≤ 30%（校準標本 ≤ 15%），**或**絕對全距在該指標的雜訊底線內。
⚠️ 只看相對離散度會把方向搞反：治療有效正是讓分母趨零，
於是「治療越成功，越判它不可重現」。底線取指標自己的量子
（掉幀 5 幀 / INP 16ms＝兩格 8ms 量化 / CLS 0.01 / LCP 50ms）。

#### 兇手歸因

| | ⟨病變⟩ | ⟨治療⟩ |
|---|---|---|
| inputDelay | ⟨ms⟩ | ⟨ms⟩ |
| processing | ⟨ms⟩ | ⟨ms⟩ |
| presentation | ⟨ms⟩ | ⟨ms⟩ |
| LoAF forcedStyleAndLayout（僅標本自己的 script） | ⟨ms⟩ | ⟨ms⟩ |
| sourceFunctionName | ⟨函式名⟩ | ⟨函式名⟩ |

三輪兇手段是否一致：⟨是 / 否，不一致就不得宣稱歸因⟩

> `presentation` 繼承 `duration` 的 8ms 量化，會落在 8ms 網格上。
> 對量級對照無影響，只在替兩個都已經很快的方案排名時咬人。
> `blockingDuration` 是整幀的值，**含外殼**，規格上無法拆到單一 script；
> `forcedStyleAndLayoutDuration` 是逐 script 的，所以只有它能乾淨濾掉外殼貢獻。

#### 治療梯度

| 治療 | 主指標 | 相對病變 | 代價 |
|---|---|---|---|
| ⟨治療一⟩ | ⟨值⟩ | ⟨n×⟩ | ⟨相容性 / 複雜度 / 換來的新問題⟩ |
| ⟨治療二⟩ | ⟨值⟩ | ⟨n×⟩ | ⟨…⟩ |

治療版落進雜訊底線時**不報比值**。
「716ms ÷ 0.1ms ＝ 7163 倍」描述的是除數多小，不是治療多有效；
誠實的寫法是「治療版該指標為零」。

無效或反向的治療照實寫。**一個沒效的治療比三個有效的更值得寫** ——
它說明成本落在讀者以為的位置以外。

#### 與登記的差異

逐條對照，三種結局分開寫：

- **符合**（誤差 ≤ 30%）：⟨列出⟩
- **數值落空**（同方向但差一個數量級）：⟨列出⟩ → 先懷疑量測，不是先改結論
- **方向落空**（結論相反或兇手不同）：⟨列出⟩ → **這是最好的素材，照實寫，不准改設計去迎合登記**

處置順序固定：① 查環境（其他分頁 / 背景下載 / throttle 宣告與實際不符）
② 換更精確的驅動方式 ③ **最後**才動 protocol —— 動它會讓已有數字作廢。

#### 誠實揭露

必填。沒有要寫的就寫「無」，不要刪掉這一節。

- 這個標本**沒有**示範的東西：⟨例如：用系統字族替代真正的自架 webfont，機制為真但故事不完整⟩
- 已知會讓數字失真的因素：⟨例如：錨點的機器相依性、驅動器保真度⟩
- 換機器後必須重跑什麼才能沿用結論：⟨例如：先重跑校準錨點 B 重新校準單位成本⟩
- 本輪未做的事：⟨例如：人手複驗、web-vitals 對帳⟩

## 已填範例：#3 強制同步版面重排

### 03 強制同步版面重排（Layout Thrashing）

**病症一句話**：對 800 列的清單交替「讀 `offsetHeight`、寫 `width`」，
每次點擊觸發約 0.7 秒的強制同步版面重排；讀寫分離之後，強制版面**一幀都不再產生**。

#### 凍結條件

| | |
|---|---|
| CPU throttle | 4x（宣告值） |
| 驅動方式 | CDP 機器驅動（`Input.dispatchMouseEvent`） |
| viewport | 800 × 600 |
| refreshHz | 實測值寫進 `RunConditions.device.refreshHz` |
| 操作程序 | click · 10 次 · 間隔 2500ms |
| buildId | 見 `docs/measurements/2026-07-25-reproducibility-4x.json` |
| protocolVersion | 1 |

#### 動工前登記的預期

> 登記出處：`docs/phase1-expected-results.md`（標本 #3 段）

- 主指標 `loaf.forcedStyleAndLayout`，預期 **200~500ms（1x）**
- 兇手段預期 **processing** —— 與標本 #1 的 inputDelay 形成對照，這個對照就是文章骨架
- 病變 vs 治療比值預期 **> 20×**
- 登記在案的風險 #2：治療版可能**不是數字小，是沒有數字**

#### 實測

| mode | 三輪 forced median | 相對離散度 | 絕對全距 | 判定 |
|---|---|---|---|---|
| broken 交替讀寫 | 744.5 / 716.4 / 678.3 ms | 9.2% | 66.2ms | ✅ 可重現 |
| fixed-batched 讀寫分離 | 0.1 / 0 / 0 ms | — | 0.1ms | ✅ 可重現（在雜訊底線內） |

INP median 另計：病變 788 / 772 / 720ms（8.8%），治療 48 / 44 / 48ms（16×）。

4x 對 1x 的換算檢核：同一份程式的 1x 探針（四次點擊）量到 159.5 / 170.4 / 187.4 / 187.4ms，
median 178.9ms；4x 的三輪 median 中位是 716.4ms，比值 **4.0×**。
兩邊都是「每次點擊的 forced 值」，基準相同 —— 節流確實生效，不是宣告了沒套用。

#### 兇手歸因

| | broken | fixed-batched |
|---|---|---|
| inputDelay | 0.8 ~ 1.1 ms | 0.9 ~ 1.1 ms |
| processing | 781.9 ~ 1082.5 ms | 6.8 ~ 9.9 ms |
| LoAF forcedStyleAndLayout | 678 ~ 745 ms（median） | 三輪裡兩輪**零幀** |
| sourceFunctionName | `interleavedReadWrite` | —（沒有幀可指認） |

三輪兇手段一致：**processing**。與 inputDelay 差三個數量級。

`sourceFunctionName` 能讀出來是因為 build 開了 `keepNames`；
沒有它，證據只會指向一串 minify 後的單字母。

#### 治療梯度

| 治療 | forced median | 相對病變 | 代價 |
|---|---|---|---|
| 讀寫分離（先全讀進 `Int32Array`，再全寫） | 0 ms | 治療版該指標為零 | 需要一塊暫存；讀與寫不能再交錯寫在同一個迴圈裡 |

`layoutChecksum` 兩臂皆 54168 —— 讀寫分離**沒有偷工**，最終 DOM 完全相同。
這個檢核必須有：否則「治療版比較快」最無聊的解釋就是它少做了事。

#### 與登記的差異

- **符合**：兇手段 processing ✅；比值 > 20× ✅（實際是治療版歸零）
- **數值落空**：登記 200~500ms 是 1x 的值，實測在 4x。換算回 1x 約 170~186ms，
  比登記下緣低 ~7%，在 30% 帶內，**不調 N**
- **方向落空**：無
- **登記風險 #2 成真**：治療版不是數字小，是沒有數字。已據此改寫判定邏輯 ——
  「有取樣但零筆」與「沒量到」必須分開，否則會被判成「樣本不足」

量測過程中修掉的**儀器**缺陷（不是標本缺陷）：
第一版拿 forced **峰值**跨輪比，算出離散度 52%，判定不可重現；
改用每輪 median 之後是 9.2%。**不可重現的是儀器。**
第二輪的離群點（單次 processing 1082ms、輪內 spread 62%）被 median 吸收 ——
這組資料自己證明了「判定用 median 不用 max」這條規則。

#### 誠實揭露

- 這個標本**沒有**示範的東西：只示範了一種讀寫交錯樣式（讀 `offsetHeight` / 寫 `width`）。
  沒有涵蓋 `getComputedStyle`、`scrollTop`、`getBoundingClientRect` 等其他強制重排觸發點
- 已知會讓數字失真的因素：N = 800 是由校準錨點 B 反推的，
  而錨點 B 機器相依性極高（同一份程式在不同 headless 設定下曾差 30 倍）
- 換機器後必須重跑什麼：**先重跑校準按鈕 B**，重新校準單次強制版面的單位成本，
  再看 N = 800 的預期還成不成立
- 本輪未做的事：人手複驗（本輪全部是 CDP 機器驅動）；
  `?validate=1` 的 web-vitals 對帳未納入這輪三輪量測
