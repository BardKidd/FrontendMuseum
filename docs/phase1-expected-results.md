|---|---|
| 和預期差在 **30% 以內** | 接受，往下走 |

## 通過條件（§1 原則 4，`spec:55-57`）

每個標本、每個 mode 連跑三輪，三個都要成立：

1. 三輪的病變／治療中位數比值，都落在**同一個量級帶**
2. 三輪的**兇手段一致** —— 不會這輪 processing 爆掉、下輪變成 input delay
3. 三輪病變值的相對離散度 **≤ 30%**（`(max - min) / median`）

不通過**不代表數字不可信，代表有一個變因沒凍住**。修變因，不修結論。

## 預期值綁定的條件

以下所有數字都只在這組條件下有效。換任何一項，數字全部作廢：

- CPU throttle **4x**（DevTools 設定 + 面板下拉宣告，兩邊都要）
- viewport **800×600**（`FROZEN_VIEWPORT`，`src/specimens.ts:10`）
- 依各標本 `meta.protocol` 的 action / repetitions / intervalMs
- build 產物（`npm run measure`），不是 dev server
- 同一台機器、同一個 `refreshHz`

另外登記一組 **1x（未節流）** 的預期，因為 `tools/acceptance.mjs` 跑在 1x，
兩組數字要能各自對照，不能混著比。

## 錨點：這些預期不是猜的

Phase 0 留下兩個實測錨點，下面的推估全部從它們外推：

**錨點 A —— 忙迴圈的解析解。** `00-calibration` 按鈕 A 設 300ms，
驗收第 2 條實測 `processing = 300.6ms`（誤差 0.2%）。
意思是：**只要負載是主執行緒同步佔用，`processing` 段就等於佔用時間，量測層不會騙人。**

**錨點 B —— 強制版面重排的單位成本。** `00-calibration` 按鈕 B，M=200 次讀寫交替、
標的內含 600 個子元素、寫的是 `width`（逼文字重新斷行）：

| 來源 | 實測 |
|---|---|
| `README.md:76` | 66.9ms |
| 稽核重跑 | 76.4ms |
| 本次重跑 | 62.2ms |

→ **1x 下每次強制同步版面約 0.31~0.38ms**（M=200，600 子元素）。

⚠️ **這個單位成本機器相依性極高。** `specimens/00-calibration.ts:31` 記著：
「同一份程式在不同 headless 設定下差了 30 倍」。所以錨點 B 只能拿來推**同一台機器**上的量級，
不能跨機器搬。標本 #3 的預期若在別台機器上量，先重跑一次按鈕 B 重新校準單位成本。

## 標本 #1 — 主執行緒阻塞

**⚠️ 誠實揭露：這不是盲預測。** 標本 #1 已經實作完成（`0014c92`），我讀過它的程式碼才寫下這些數字。
它仍然是可否證的 —— 因為**這個標本從來沒有跑過三輪可重現量測**，下面的數字都還沒有人量過。
但它比標本 #3 的預測弱，判讀時要記得這個差別。

**負載**：`ORDER_COUNT = 50_000`，固定種子 `20240117`（`specimens/01-main-thread-block.ts:40,47`）。
多欄位比較器 `compareOrders` + 分區彙總。

**兇手宣告**：`culprit: 'inputDelay'`（`src/specimens.ts:87`）。
理由記在 `src/specimens.ts:55-57`：單獨點一下只會看到 processing 爆掉，
**要連打才會看到事件排在後面等主執行緒**。所以 `protocol.intervalMs = null`。

### 預期值

| mode | 指標 | 1x 預期 | 4x 預期 |
|---|---|---|---|
| `broken` | 單次 `sortMs`（標本自報） | 25~60ms | 100~240ms |
| `broken` | **INP（兇手 = inputDelay）** | 150~500ms | **500~1500ms** |
| `broken` | `loaf.specimenScriptDuration`（代表幀） | 25~60ms | 100~240ms |
| `fixed-yield` | INP | **< 50ms** | **< 80ms** |
| `fixed-yield` | 單次 `sortMs`（含讓出時間） | 比 broken **長**（40~120ms） | 比 broken 長 |
| `fixed-worker` | INP | **< 30ms** | **< 50ms** |
| `fixed-worker` | 主執行緒序列化 | 5~20ms | 20~80ms |

**比值預期**：`broken / fixed-yield` **≥ 5×**，`broken / fixed-worker` **≥ 10×**。

### 三個要注意的方向性預測

1. **`fixed-yield` 的 `sortMs` 會比 `broken` 更長，這不是 bug，是重點。**
   切 chunk + 讓出，總工時一定變長（多了排程開銷），但**互動延遲塌下來**。
   標本檔 `:207` 已經寫了「對自己不利的方向偏，結論反而更硬。兩邊的 `sortMs` 都有上報，讀者自己看得到」。
   若量到 `fixed-yield` 的 `sortMs` **比 broken 短**，那是量測錯了，不是好消息。

2. **兩段治療之間不排名。** 預期 `fixed-worker` 的 INP 比 `fixed-yield` 低，
   但兩者都會落進「良好」區間（< 200ms），差距很可能落在 8ms 網格量化的等級。
   依 §4.3，**文章就寫「兩者都把 INP 壓進良好區間」**，不宣稱誰贏。

3. **兇手段必須是 `inputDelay`。** 若三輪裡有任何一輪的兇手變成 `processing`，
   §1 原則 4 第 2 條就不通過 —— 那代表連打的節奏不夠快，事件沒有真的排隊。

### 這個標本最大的可重現性風險

**`intervalMs = null`（連打）不是一個真正凍結的變因。**

其他所有變因都凍住了（viewport、種子、build、throttle），但「盡快連續點十次」的實際節奏
取決於操作者的手速，而且**畫面凍結時操作者會下意識放慢**。
input delay 的大小直接由「點擊間隔 vs `sortMs`」的比例決定 ——
間隔 80ms 配 `sortMs` 150ms 會累積出很大的 backlog，間隔 200ms 配同一個 `sortMs` 幾乎不累積。

**預測：這個標本三輪的離散度會是全站最高的，而且很可能就卡在 30% 這條線上。**

若三輪離散度 > 30%，處置順序（修變因，不修結論）：
1. 先確認不是其他分頁 / 背景下載 / 忘了開 throttle
2. 再考慮改用 `tools/acceptance.mjs` 的程式化點擊取得同一組數字 ——
   CDP 派送的時序是機器控制的，人手的變異在那裡完全消失
3. **最後才考慮改 `protocol`** —— 那會讓已有的數字作廢，而且 `intervalMs: null` 是刻意的設計決定

## 標本 #3 — 強制同步版面重排（Layout Thrashing）

**這是真正的盲預測** —— 標本還沒開始寫，下面每個數字都是動工前登記的。

spec 對它的定位（`spec:1067`）：「**這是整套最值得寫的一個**」「**也是全站數字最可信的標本**，
因為 `forcedStyleAndLayoutDuration` 是逐 script 的，外殼貢獻可以乾淨濾掉」。

### spec 已經給了一個預期，先照抄

`spec:1353` 逐字：

> 「病變版 `forcedStyleAndLayout` 應在 200~500ms，治療後 < 10ms，比值 > 20×」

**這是作者自己寫的預期，我不覆蓋它，只補上它沒有的部分。**

### 動工前登記的設計參數

要讓上面那個預期可否證，得先釘住負載規模。用錨點 B 反推：

- 1x 下每次強制同步版面約 **0.31~0.38ms**（600 子元素的標的）
- 要打到 200~500ms，需要約 **530~1600 次**強制重排

但標本 #3 的形狀跟按鈕 B 不同：spec 的病變片段是**在 N 個各別元素上**讀寫，
每次寫髒的是整份 document 的 layout，所以單次成本會**隨列表總節點數上升**，
不是固定的 0.31ms。

**登記的設計參數（動工時照這個做，改了要在下面記一筆）**：

| 參數 | 值 | 理由 |
|---|---|---|
| 列表元素數 N | **800** | 落在錨點 B 反推的 530~1600 中段 |
| 每個元素的內容 | 一行文字 + 一個 badge | 太乾淨會讓每次結算便宜到接近 0（按鈕 B 踩過這個坑，`00-calibration.ts:104-105`） |
| 讀取屬性 | `offsetHeight` | 與 spec 片段一致 |
| 寫入屬性 | **`width`** 而非 `height` | 逼文字重新斷行，才是貨真價實的版面計算。理由同 `00-calibration.ts:103-107` |
| 資料 | 固定種子 | 同 #1，可重現性優先於真實感 |

### 預期值

| mode | 指標 | 1x 預期 | 4x 預期 |
|---|---|---|---|
| `broken`（交替讀寫） | **`loaf.specimenForcedStyleAndLayoutDuration`** | **200~500ms** | 600~2000ms |
| `broken` | INP（兇手 = `processing`） | 250~600ms | 700~2200ms |
| `fixed-batched`（讀寫分離） | **`forcedStyleAndLayout`** | **< 10ms** | < 25ms |
| `fixed-batched` | INP | < 60ms | < 100ms |

**比值預期**：`broken / fixed-batched` 的 `forcedStyleAndLayout` **> 20×**（照抄 spec）。

**兇手段預期**：`processing`（不是 `inputDelay`）。
強制重排發生在事件處理器**內部**，所以它撐大的是 processing 段。
這與標本 #1 形成對照 —— **同樣是主執行緒被佔住，兇手段不同**，這個對照本身就是文章的骨架。

### 最可能出錯的地方（動工前先想清楚）

1. **N=800 在這台機器上打不到 200ms。**
   錨點 B 的單位成本機器相依性是 30 倍等級。若量到只有 30~50ms，
   **先調 N（那是校準），不要調預期**。調完在下面記一筆新的 N 與理由。

2. **LoAF 只回報 ≥ 50ms 的幀。** 治療版預期 < 10ms，意思是**治療版很可能根本不產生 LoAF entry**。
   那不是「數字很小」，是「沒有數字」。面板與文章都要能正確呈現「沒有 entry」與「entry 是 0」的差別 ——
   `00-calibration.ts:25-26` 已經踩過這個坑，第 7 條驗收差點因此掛掉。

3. **`forcedStyleAndLayoutDuration` 混入外殼貢獻。**
   spec 說這個標本「數字最可信」正是因為這個欄位逐 script 歸因、外殼可以濾乾淨。
   若量到治療版的 `forcedStyleAndLayout` 不趨近 0 而是卡在某個底線，
   先確認那個底線是不是外殼自己的版面計算被算進來了。

4. **方向相反的情況**：若「讀寫分離」沒有讓 `forcedStyleAndLayout` 掉下來，
   最可能是寫入的值每輪相同，瀏覽器判定 layout 沒被弄髒 ——
   `00-calibration.ts:119-120` 記了同一個陷阱。那時候不是結論錯，是病變版根本沒病。

### 2026-07-25 — 標本 #3 動工

**N 沒有改，維持登記的 800。** 下面補登三組原登記表沒有涵蓋的參數，並記一次校準探針的結果。

#### 一、補登的設計參數（原登記表沒有這三項）

| 參數 | 值 | 理由 |
|---|---|---|
| `protocol.intervalMs` | **2500ms** | 登記的 4x 病變上限是 2000ms。間隔若不大於那個上限，節流下第 k 次點擊會落在第 k-1 次還沒跑完時，事件開始排隊，**兇手段會從 `processing` 翻成 `inputDelay`** —— §1 原則 4 第 2 條當場不通過。若某台機器 4x 病變超過 2500ms，要調的是這個間隔 |
| `protocol.repetitions` | **10** | 不是隨手填的：`App.tsx:437` 的「已記錄 n / N」門檻取自 `protocol.repetitions` 而非 `MEASURE_CONFIG.minInteractions`（兩者今天同為 10 但沒有程式耦合）。填小於 10 的值，面板會在有效樣本不足 10 時顯示「已達標」 |
| 列的行高 | **24px**（寫死在標本注入的 style） | 用來證明「每次點擊寫入的寬度都與上次不同」：Δh 必為 24 的倍數，寬度相位每次前進 13，(Δh + 13) mod 120 = 0 需要 24k ≡ 107 (mod 120)，不可能。寬度寫成同一個值會讓病變版安靜地治好自己 |

寬度範圍 240~359px、相位步進 13、種子 20240303 一併凍結，理由寫在 `specimens/03-layout-thrashing.ts` 的 `widthForRow`。

#### 二、N=800 的校準探針（**不是三輪正式量測**）

條件：headless Brave + CDP 派送真實輸入、**1x 未節流**、四次點擊、間隔 2500ms。
正式的三輪可重現量測還沒跑，這一次只回答「N=800 打得到登記的量級嗎」。

| mode | 量到的 | 登記的 1x 預期 |
|---|---|---|
| `broken` `specimenForcedStyleAndLayout` | 159.5 / 170.4 / 187.4 / 187.4 ms | 200~500ms |
| `broken` INP（`inputDelay` 0.5 / `processing` 193.6） | 200ms，**兇手 = processing** ✅ | 250~600ms，兇手 processing |
| `fixed-batched` `forcedStyleAndLayout` | **完全沒有 LoAF entry** | < 10ms |
| `fixed-batched` INP（`processing` 2.2 / `presentation` 29.5） | 32ms | < 60ms |
| `sourceFunctionName` | `interleavedReadWrite` | —— |

**最高的 187.4ms 比登記下限 200ms 低 6.5%，落在「30% 以內接受，往下走」那一格，所以不調 N。**
調大 N 讓它撞進 200~500 是修結論不修變因 —— 預期本來就寫了帶寬，量在帶寬邊緣不是失敗。

三件登記在案的風險，探針各給了答案：

1. **「N=800 打不到 200ms」** —— 幾乎踩線但沒踩破，且方向與量級都對。維持 800
2. **「治療版可能根本不產生 LoAF entry」** —— **成真了**。治療版一幀都沒有，
   不是「數字很小」是「沒有數字」。面板與文章都必須能區分「沒有 entry」與「entry 是 0」
3. **「治療版的 `forcedStyleAndLayout` 卡在某個底線 = 外殼混進來」** —— 沒發生。
   病變版那幾幀的 `shellScript` 是 0.0ms，spec 說這個標本數字最乾淨，確認為真

#### 三、探針順帶產生的兩個文章素材（不是修正，是發現）

- **`layoutChecksum` 兩臂完全相同（54168）。** 讀寫分離沒有偷工，兩個 mode 的最終 DOM 一模一樣，
  差的只有成本。這個等式是標本自己每次點擊都在驗的，不是我宣稱的
- **治療版的 INP 32ms 裡有 29.5ms 是 `presentation`。** 那一次必要的版面計算沒有消失，
  只是從 script 內移到瀏覽器的正常繪製步驟（記在 `styleAndLayoutDuration` 不是
  `forcedStyleAndLayoutDuration`）。**省下來的是 799 次多餘結算，不是那一次必要的結算** ——
  文章照這個講，講成「讀寫分離讓版面計算消失」就是誇大
